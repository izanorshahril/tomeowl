# Choose the evidence atlas UI direction

**Label:** wayfinder:map
**Tracker:** local Markdown
**Status:** direction and bounded UI implementation complete; future capability gates remain separately tracked

## Destination

Make the current project ready for a coherent, independently reviewed UI iteration: a recognizable local evidence atlas with project/research examples, optional 3D, a clear evidence path, and lean preparation for the researched requirements.
The current acceptance contract is the [UI slice](../../SPEC.md#ui-design-slice-2026-10-03), and actual completion evidence belongs in the status and UI review documents.

## Notes

The user explicitly authorized autonomous recommendations, self-critique, implementation, local specification/ticket preparation, and repeat UI review without an interview.
The records below capture agent-selected direction under that authorization and do not represent a simulated human exchange.
This effort uses codebase-design, improve-codebase-architecture, prototype, impeccable, research, to-spec, to-tickets, and wayfinder as applicable.
Keep the existing portable catalog/viewer, ordinary source files, independent view state, and truthful relation provenance.
Use a local tracker; the map indexes decisions and does not duplicate their detailed resolutions.

## Decisions so far

- [Keep the existing evidence core and deepen projection](keep-evidence-core.md): one shared presentation seam concentrates grouping and provenance rather than introducing a framework or graph store.
- [Start with a readable atlas and keep 3D optional](readable-atlas.md): corpus overview, collection neighborhood, and evidence form the primary navigation path.
- [Use real project and research samples](real-samples.md): bounded local inputs demonstrate structure and references without claiming a full literature-review capability.

## Not yet specified

Future multi-format evidence and numerical/program workflows need concrete public fixture selection, target deployment evidence, and consumers before parser, engine, or renderer decisions become useful.
Expand the E1 literature effort from one offline bibliography-to-passage journey, then decide provider, PDF/OCR, and richer locator work from observed limitations.
Similarity and extraction should follow a held-out corpus and useful discovery question, with review/status semantics and calibrated score meaning before a presentation is designed.
These areas belong to later capability maps, not blockers for the current UI slice.

## Out of scope

Automatic scholarly synthesis, corporate data onboarding, numerical measurement/STDF processing, program runtime analysis, model installation, harness writes, durable memory, multiuser deployment, and a graph-engine replacement are beyond this map's destination.
The existing future specifications retain those capability requirements and evidence gates.
