# Memory and Knowledge Systems - Additional Research

Research date: 2026-10-01. This is a supplement to [RESEARCH.md](RESEARCH.md), not a product specification. Claims below are based on project-owned repositories or documentation; marketing and benchmark claims are identified as such. GitHub popularity figures are an observed snapshot, not a quality measure.

## Findings that change the plan

- Keep the product centered on a local, source-grounded knowledge index that can serve both project repositories and engineering documents. Treat memory capture/consolidation and document RAG as separate workflows over shared sources and provenance; coding-agent products generally do not solve ATE document extraction or structured test-data joins.
- Use QMD and Graphify as existing tools through adapters first. Avoid adopting a second full indexing stack until a measured retrieval gap appears. None of the surveyed projects establishes a need for a standalone graph database: useful relation graphs can begin as extracted, inspectable records with source links.
- Make scopes, provenance, correction/deletion, freshness, and access labels part of the data model from the start. A result must carry its source path/page/section/record and extraction version. Buzz and Paperclip illustrate why scope and audit trails belong to the integration contract, not only the search index.
- Keep ingestion writes asynchronous and recall bounded. Rich extraction and enrichment can cost more than querying; make extraction jobs inspectable, resumable, and optional. Let retrieval return concise evidence first, with explicit expansion for surrounding context.
- Do not set performance targets such as “40% token savings” as established facts. The existing [RESEARCH.md](RESEARCH.md) contains broad system-specific claims and prescriptive implementation choices without nearby primary-source citations; its 40% figure is not substantiated there. Treat all such numbers as hypotheses to measure against a fixed local query set.

## What to prototype against local projects and ATE material

1. Establish a small benchmark with both workspace queries (prior decisions, “where is this implemented?”) and engineering queries (ATE manual limits/procedures, test program identifier, schematic net/pin, datasheet spec). Score source correctness, page/line precision, freshness, retrieval latency, and injected-token count; keep queries and expected source spans under version control.
2. Model each ingested object with stable source identity, revision/hash, document family, scope, page/section/line locator, and parser version. Preserve the source; treat extracted text, tables, entities, and relations as rebuildable derivatives.
3. Start with existing QMD for text retrieval and Graphify for code structure, behind a small adapter contract. Add document-family parsers incrementally; for PDFs/schematics, require page/image anchors and human-verifiable extracted tables. Keep numerical limits, units, conditions, revision/effective date, and pin-net mappings structured instead of relying on embedding similarity.
4. Add only the minimum durable memory loop: explicit remember/forget/correct, session source links, scoped Markdown notes, and optional scheduled consolidation. Evaluate semantic embeddings, graph traversal, and LLM extraction as optional stages against the benchmark before making them required.

## Source audit note

The existing [RESEARCH.md](RESEARCH.md) is useful as a hypothesis catalog, but its detailed descriptions of Oh My Pi, Jcode, Hermes, OpenClaw, GBrain, QMD, Graphify and the proposed Tomeowl stack need a claim-by-claim citation pass before implementation decisions rely on them. In particular, the cited 40% token-reduction number is not supported in that document, and its chosen Rust/SQLite/vector/graph combination is a proposal rather than an evidence-backed requirement. This supplement makes no claim that any one surveyed architecture is the universal winner.
